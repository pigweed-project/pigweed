-----------------------
Tokenized log arguments
-----------------------
.. pigweed-module-subpage::
   :name: pw_log

The ``pw_log`` facade is intended to make the logging backend invisible to the
user, but some backend features require additional frontend support,
necessitating a break in the abstraction. One of these features is the logging
of nested token arguments in tokenized logs, because only the user is able to
know which log arguments can be tokens (see :ref:`module-pw_tokenizer` for
context on tokenization, and :ref:`module-pw_log_tokenized` for an example of
a tokenized logging backend). Arguments that have already been tokenized are
just unsigned integers, and not all strings can be compile-time constants, so
users must be provided with a way of manually marking token arguments.

To this end, ``pw_log/tokenized_args.h`` aliases macros from ``pw_tokenizer``
to enable logging nested tokens when the active backend uses tokenization.
These alias macros revert to plain string logging otherwise, allowing projects
to take advantage of nested token logging without breaking readable logs when
the project is built with a different logging backend. To support logging
nested token arguments, a ``pw_log`` backend must add an empty file
``log_backend_uses_pw_tokenizer.h`` under ``public_overrides/pw_log_backend/``.

Although the detokenizing backend accepts several different numeric bases, the
macros currently only support formatting nested tokens in hexadecimal, which
affects how the arguments appear in final logs if they cannot be detokenized
for any reason. Undetokenized tokens will appear inline as hex integers
prefixed with ``$#``, e.g. ``$#34d16466``.

Inline string arguments
=======================
.. code-block:: cpp

   #include "pw_log/tokenized_args.h"

   #include "pw_log/log.h"

   // bool active_
   PW_LOG_INFO("Component is " PW_LOG_TOKEN_FMT(),
               active_ ? PW_LOG_TOKEN_EXPR("active") : PW_LOG_TOKEN_EXPR("idle"));

Logging enums and status codes
==============================
``PW_LOG_ENUM`` and ``PW_LOG_ENUM_VERSIONED`` log enumerators as tokens on
tokenizing backends and strings on non-tokenizing backends, evaluating their
argument once. With ``pw_log/status.h`` (``//pw_log:status``) included, they
also log the status code of ``pw::Status``, other statuses with enum codes,
``pw::StatusWithSize``, and ``pw::Result``:

* **Static domain (1 vararg)**: Pair generated ``<ENUM>_FMT``,
  ``<STATUS>_CODE_FMT``, or :cc:`PW_STATUS_CODE_FMT` with :cc:`PW_LOG_ENUM`.
* **Generic / versioned domain**: Pair :cc:`PW_LOG_ENUM_VERSIONED_FMT` with
  :cc:`PW_LOG_ENUM_VERSIONED` in templates or code that does not know the
  concrete enum macro name.

``I2cStatus`` and the ``MY_DRIVER_I2C_STATUS_*`` macros in the examples below
are generated by ``pw_enum``. See :ref:`module-pw_enum-status-logging`.

.. code-block:: cpp

   #include "pw_log/log.h"
   #include "pw_log/status.h"

   void LogTransferCode(pw::Status status) {
     // Static domain (1 argument):
     PW_LOG_INFO("Transfer code: " PW_STATUS_CODE_FMT, PW_LOG_ENUM(status));
   }

   template <typename EnumOrStatus>
   void LogGenericCode(const EnumOrStatus& value) {
     // Versioned domain (works for any pw_enum enum or status):
     PW_LOG_INFO("Code: " PW_LOG_ENUM_VERSIONED_FMT(),
                 PW_LOG_ENUM_VERSIONED(value));
   }

Logging statuses with optional messages
=======================================
``pw::Status`` and other ``pw::StatusBase``-derived statuses may carry an
optional error message created with ``PW_STATUS_MSG("...")`` (see
:ref:`module-pw_status-messages`). :cc:`PW_LOG_STATUS` from ``pw_log/status.h``
logs ``"CODE: message"`` if the status has a message and ``"CODE"`` otherwise.
Pair it with :cc:`PW_STATUS_FMT` for ``pw::Status``, or with a generated
``<STATUS>_FMT`` macro.

.. code-block:: cpp

   #include "pw_log/log.h"
   #include "pw_log/status.h"

   void HandleStatus(pw::Status status, const I2cStatus& i2c_status) {
     PW_LOG_WARN("Read failed: " PW_STATUS_FMT, PW_LOG_STATUS(status));
     PW_LOG_WARN("I2C transfer failed: " MY_DRIVER_I2C_STATUS_FMT,
                 PW_LOG_STATUS(i2c_status));
   }

``PW_LOG_STATUS`` evaluates its argument once and expands to one log argument.
To log the status of a ``pw::Result`` or ``pw::StatusWithSize``, pass the object
itself (``PW_LOG_STATUS(result)``).

How the status is logged depends on how status messages are stored, which is
set with :cc:`PW_STATUS_CFG_MESSAGES` (see
:ref:`module-pw_status-messages-config`):

* :cc:`PW_STATUS_CFG_MESSAGES_NONE` (the default): the status code, as with
  ``PW_LOG_ENUM``.
* :cc:`PW_STATUS_CFG_MESSAGES_TOKENIZED`: one 32-bit value with the code in its
  low bits and the message's token in the rest, logged as a
  :ref:`bit field token <module-pw_tokenizer-bit-field-tokens>`. The message's
  token is in the domain of the status's code followed by ``::Message`` (e.g.
  ``::pw::Status::Message``). Bit field tokens are currently only decoded by
  the Python detokenizer.
* :cc:`PW_STATUS_CFG_MESSAGES_STRING`: one string, formatted into a temporary
  buffer of :cc:`PW_LOG_STATUS_STRING_SIZE` bytes that exists until the end of
  the log statement. Longer text is truncated. The backend must use the string
  before the log statement returns.

``PW_STATUS_CFG_MESSAGES`` must match the ``pw_log`` backend: tokenized
messages for backends that tokenize logs, string messages otherwise.
``pw_log/status.h`` fails to compile with an explanation if they do not match.
